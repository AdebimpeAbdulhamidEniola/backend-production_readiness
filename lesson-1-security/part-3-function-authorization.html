Lesson 1 · Security · Part 3

The endpoints nobody guarded

You'll test every route from login to the end and discover that a whole group of them was wired up without the auth check. Here it fails shut — but the same mistake is how data leaks.

Severity: Medium OWASP API5:2023 — Broken Function Level Authorization

A production security pass means walking every endpoint and asking two questions: "is authentication enforced here?" and "is it enforced the same way as its neighbours?" Inconsistency between routes is where attackers live. Let's audit the router.

Where the hole is

Compare two route files. Transactions (src/routes/transaction.routes.ts) guard every route:

router.post("/", authenticate, validateBody(...), createTransactionController);
router.get("/",  authenticate, getTransactionController);

But reports (src/routes/report.routes.ts) have no authenticate at all:

router.get("/monthly", getMonthlyReport);      // ← no authenticate
router.get("/charts",  getChartsAndGraph);     // ← no authenticate

Yet both controllers do const userId = req.userId; — a value that only the authenticate middleware sets. The middleware isn't on these routes, so req.userId is always undefined.

The claim we're about to prove

The reports endpoints are broken for everyone: even a correctly logged-in user is rejected, because the route never runs the middleware that would identify them. The access-control layer was simply forgotten on this router.

Break it — in Postman

  1. Call it as a valid user. GET {{baseUrl}}/api/reports/monthly, Authorization: Bearer {{TOKEN_A}}.
    You get 401 "User not authenticated" — even though your token is valid. The report feature is dead. Alice can create transactions but can never see a report of them.
  2. Confirm it's the wiring, not your token. The same token works on GET {{baseUrl}}/api/transactions (200). So the token is fine; the reports router just never reads it.
Why this is a security lesson, not just a bug. Here the forgotten middleware fails closed (everyone is rejected), which is annoying but safe. The exact same slip — a route mounted without its guard — fails open whenever the handler doesn't depend on req.userId. That's Broken Function Level Authorization: an endpoint reachable by people who should never reach it. The discipline is the same: no route ships without a deliberate decision about its auth.

Fix it — guard the router, consistently

src/routes/report.routes.ts — apply authenticate to the whole router so no future route can be added unguarded by accident:

import { authenticate } from "@/middlewares/auth.middleware";

const router = Router({ caseSensitive: true, strict: true });
router.use(authenticate);                 // ← every route below is now protected

router.get("/monthly", getMonthlyReport);
router.get("/charts",  getChartsAndGraph);

router.use(authenticate) is better than repeating it per line: it makes "protected" the default for this router, so the next person to add a route can't forget.

Re-test

GET {{baseUrl}}/api/reports/monthly with {{TOKEN_A}} → 200 with Alice's income/expense/savings. With no token → 401. The feature works, and it works only for authenticated users.

Your turn

You found the reports router was unguarded. Now audit the profile router yourself and decide: is it guarded or not? Prove your answer in Postman before revealing.

Reveal the answer

Open src/routes/user.routes.ts: both routes include the middleware — routes.get('/', authenticate, getProfile). So profile is guarded (reports was the outlier). Prove it: GET {{baseUrl}}/api/user/profile with no Authorization header → 401; with Bearer {{TOKEN_A}} → 200 and Alice's profile. The deliverable is the audit itself: a table of every route marked guarded / unguarded / should-be. That table is the proof to an interviewer that you review access control route by route, not by assumption.
