Severity: Medium–High OWASP API8:2023 — Security Misconfiguration

Most of this lesson attacked endpoints. Misconfiguration is different: the damage is in defaults, logs, and settings. It's also the easiest category to find once you know to look — and interviewers love candidates who read boot logs and config, not just routes.

Finding 1 — the database URL in your logs

src/index.ts prints your connection string on every startup:

app.listen(port, () => {
  console.log(`Server is running at http://localhost:${port}`);
  console.log(process.env.DB_URL)   // ← your full database URL, creds and all
});

Prove it

Start the server and look at the terminal: your database URL — including the username and, in many setups, the password and host — is sitting in plain text. Now picture that same line in a cloud log aggregator (CloudWatch, Datadog, Logtail) that half your company and every integration can read. Logs get shipped, searched, and retained for years. A DB credential in a log is a DB credential leaked.

Fix

app.listen(port, () => {
  console.log(`Server listening on port ${port}`);   // no secrets, no internal URLs
});

Rule: never log secrets or connection strings. Log the fact of a connection ("database connected"), never its credentials. And rotate that DB password now — assume anything that reached a log is compromised.

Finding 2 — CORS is open to the entire internet

src/config/app.config.ts uses cors() with no options:

app.use(cors());   // ← Access-Control-Allow-Origin: *  (any website can call your API)

That lets a script on any origin make browser requests to your API. For a credentialed finance API, you want an allow-list:

app.use(cors({
  origin: process.env.ALLOWED_ORIGINS?.split(",") ?? [],  // only your frontends
  credentials: true,
}));

Finding 3 — do the small hardening the code half-started

Credit where due: the app already sets app.disable('x-powered-by') (hides the Express fingerprint) and only mounts Morgan logging outside production. Finish the set:

  • Add helmet() for safe default security headers.
  • Add express.json({ limit: "10kb" }) so a giant JSON body can't exhaust memory (ties back to Part 4's resource-consumption theme).
  • Make sure your production error path never returns stack traces — your handleUnexpectedError already returns a generic message, which is correct; keep it that way.
  • Confirm .env and serviceaccount.json are git-ignored (they are) — a leaked key file is game over.

Re-check

Restart: the boot log shows a port and nothing secret. From a browser console on some random site, a fetch to your API is now blocked by CORS. Response headers show Helmet's protections and no X-Powered-By. The quiet doors are shut.

Your turn

There's a second secrets-in-logs risk hiding in the auth flow, not the boot line. Find a place where a token or credential could end up in a log or an error, and propose the fix.

Hint: look at what gets console.error'd or returned when something fails.

Reveal the answer

Two good catches: (1) In signUp, a failed email send does console.error("Email sending failed...", emailError) — provider errors can include the recipient address and sometimes API keys in their payload, so log a sanitized message, not the raw error object. (2) The email verification token is a real credential (whoever has it can verify an account). Make sure it never appears in logs or in a generic error echoed to the client. The general rule from Finding 1 holds everywhere: log events, not secrets. We'll formalise this when we add structured logging in Lesson 5.
