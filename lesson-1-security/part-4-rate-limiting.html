Guessing passwords, unlimited tries

You'll fire a hundred wrong passwords at the login endpoint and watch it cheerfully accept every attempt. Then you'll shut the door.

Severity: High OWASP API4:2023 — Unrestricted Resource Consumption

Validation and hashing protect a single login attempt. Nothing in your API limits the number of attempts. That means an attacker can run a password list against alice@test.com until one works — "credential stuffing," one of the most common ways accounts fall.

Where the hole is

src/routes/auth.routes.ts and the login controller do validation, lookup, and comparePassword — all correct — but there is no counter, no lockout, no delay across attempts:

routes.post('/login', validateBody(logInSchema), logIn);
//            ↑ nothing here limits how often this can be hit

The guide lists this failure directly: an API that "permits credential stuffing" and "brute force attack on the same user account" is broken authentication (Backend-Engineers-Guide/notes/08_security/01_auth.md; see the rate-limiter demo in projects/security_controls_lab).

The claim we're about to prove

The login endpoint will process as many wrong-password attempts as you can send, as fast as you can send them, with no throttle or lockout — everything an attacker needs to brute-force an account.

Break it — hammer the endpoint

Postman's Collection Runner turns one request into a loop.

  1. Make a request POST {{baseUrl}}/api/auth/login with body 
    { "email": "alice@test.com", "password": "{{guess}}" }
  2. Add a small CSV data file of guesses (guess column): wrong1, wrong2, … password123 — put the real password last.
  3. Run the collection over that file (or set iterations to 100 with a random value).
    Every wrong guess returns 401 instantly, the server never slows down or blocks you, and the final row with the real password returns 200 + a token. You just brute-forced the account. A real attacker uses a list of millions, not five.
  4. Try from the command line too, to feel how fast it is: 
    for i in $(seq 1 50); do
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST {{baseUrl}}/api/auth/login \
    -H 'Content-Type: application/json' \
    -d '{"email":"alice@test.com","password":"guess'"$i"'"}'
done
    Fifty 401s, no resistance.

Fix it — limit attempts

Two layers, cheapest first.

1. A global limiter, then a strict one on auth

Install express-rate-limit. In src/config/app.config.ts add a tight limiter to the auth routes:

import rateLimit from "express-rate-limit";

const authLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,   // 15 minutes
  max: 10,                    // 10 attempts per IP per window
  standardHeaders: true,
  legacyHeaders: false,
  message: { status: "failed", message: "Too many attempts, try again later." },
});

app.use("/api/auth", authLimiter, authRoutes);  // ← limiter before the routes

Pick limits from a real budget (OWASP API4's "How To Prevent" talks in terms of maximums per client). Ten tries per 15 minutes stops a brute-force while never bothering a human who fat-fingered their password twice.

2. Don't help the attacker

Your login already returns the same 401 "Invalid email or password" whether the email or the password was wrong — good: it doesn't reveal which emails exist. Keep it that way.

Re-test

Re-run the Collection Runner: the first 10 attempts behave, then every further attempt returns 429 "Too many attempts" — including the one carrying the correct password. The attacker is throttled to a rate where a password list would take lifetimes.

Your turn

A limiter on /api/auth protects login and signup. Name one other endpoint group in this API that urgently needs its own, stricter limit — and say why.

Hint: which endpoints cost real money per call?

Reveal the answer

The AI endpoints (/api/ai/insights, /api/ai/budget). Each call triggers a paid LLM request, so an authenticated user (or a stolen token from Part 1) hammering them is a direct bill-inflation attack — OWASP API4 again, but measured in dollars, not just CPU. They deserve a much lower max than ordinary reads, and ideally a per-user quota, not just per-IP. Reports and transaction reads are cheaper but still worth a generous global limiter so one client can't starve the database.
