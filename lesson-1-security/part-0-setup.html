This part has no vulnerability — it's the foundation. By the end you'll have the server up, a database behind it, and two users (Alice and Bob) you can switch between with one click. Every later part is "log in as Bob, attack Alice."

1. Run the API

  1. In your local clone: npm install.
  2. Create .env (see README.md for the full list). At minimum you need DATABASE_URL, PORT, JWT_SECRET, JWT_EXPIRES_IN.
  3. Set up the database schema: npx prisma migrate dev then npx prisma generate.
  4. Start it: npm run dev. You should see Server is running at http://localhost:PORT.
Note what it prints. On boot the server also logs your database URL to the console. Keep that in the corner of your eye — it's a real finding we exploit in Part 5.

2. Build the Postman environment

In Postman, create an Environment called FinAI local with these variables:

baseUrl   = http://localhost:4100     (match your PORT)
TOKEN_A   =                            (Alice's JWT, filled after login)
TOKEN_B   =                            (Bob's JWT)
TX_ID     =                            (an id we capture mid-flow)

Using variables instead of pasted values is what lets you re-run the same request before and after a fix and see only the behaviour change.

3. Create two users (the "from login" starting point)

  1. Sign up Alice. POST {{baseUrl}}/api/auth/signup, body: 
    { "email": "alice@test.com", "password": "password123",
  "confirmPassword": "password123", "name": "Alice" }
    Expect 201 and "Please check your email to verify your account."
  2. Sign up Bob — same request, bob@test.com, "name": "Bob".
  3. Verify both. Login is blocked until isVerified is true, and SendGrid won't deliver on localhost without keys. For local testing, flip the flag directly: 
    psql "$DATABASE_URL" -c 'UPDATE "User" SET "isVerified" = true;'
    This is a local shortcut only. In Part 1 you'll see the real verification-token flow and why it matters.
  4. Log in Alice. POST {{baseUrl}}/api/auth/login, body { "email": "alice@test.com", "password": "password123" }. In the response, data.token is Alice's JWT — paste it into the TOKEN_A environment variable.
  5. Log in Bob → paste into TOKEN_B.

Make switching users one click

On your transaction/report requests, set the Authorization header to Bearer {{TOKEN_A}}. To "become Bob," change that one word to {{TOKEN_B}}. That's the core move of every attack in this lesson.

4. Smoke-test the happy path

Confirm a normal, legitimate flow works before you try to break it — otherwise you won't know whether a later failure is the bug or your setup:

POST {{baseUrl}}/api/transactions   Authorization: Bearer {{TOKEN_A}}
{ "amount": 5000, "category": "Salary", "type": "INCOME" }
→ 201, copy data.id into TX_ID

GET  {{baseUrl}}/api/transactions    Authorization: Bearer {{TOKEN_A}}
→ 200, you see the transaction you just made

Your turn

Add a third user, Carol, entirely on your own, and prove she can use the API — no step-by-step this time.

You have everything you need from the walkthrough above. Give it a real try before you reveal the answer.

Reveal the answer
  1. POST {{baseUrl}}/api/auth/signup with carol@test.com / "name": "Carol".
  2. Verify her: psql "$DATABASE_URL" -c 'UPDATE "User" SET "isVerified" = true WHERE email = '"'"'carol@test.com'"'"';'
  3. POST {{baseUrl}}/api/auth/login as Carol → paste data.token into a new TOKEN_C variable.
  4. POST {{baseUrl}}/api/transactions with Bearer {{TOKEN_C}} → 201. Then GET the same route → you see only Carol's transaction, not Alice's or Bob's. That isolation is what Part 2 is about.
