Severity: Critical OWASP API2:2023 — Broken Authentication

A JWT is only as trustworthy as the secret it's signed with. If an attacker can guess or obtain that secret, they can sign a token that says "I am user X" and your server will believe it. Let's see where your code gives the secret away.

Where the hole is

Open src/utils/auth.utils.ts:

const JWT_SECRET = process.env.JWT_SECRET || "default_secret";
//                                          ↑ if the env var is missing,
//                                            the signing key becomes a public string
export const generateToken = (id, email, name) =>
  jwt.sign({ id, email, name }, JWT_SECRET, options);

Two problems compound here:

  1. If JWT_SECRET is ever unset (a forgotten env var in a new deploy, CI, or a teammate's machine), the key silently becomes the literal string "default_secret".
  2. Your repo is public, so that fallback is known to the whole internet. There is nothing to guess.

The guide warns about exactly this: tokens must use "weak or predictable" secrets as a red flag (Backend-Engineers-Guide/notes/08_security/01_auth.md; see also projects/security_controls_lab's JWT demo on signing and verification).

The claim we're about to prove

If the server runs without JWT_SECRET set, anyone can craft a token for any user id and call protected endpoints as that user — full account takeover, no password required.

Break it — forge a token

We simulate the misconfiguration (an unset secret) so you can see the consequence safely on your own machine.

  1. Reproduce the misconfig. Stop the server. Comment out / remove JWT_SECRET from .env. Restart npm run dev. The app still boots happily — that silence is the danger.
  2. Find a victim's id. In a real breach the attacker gets this from any endpoint that leaks an id (a public profile, a shared document, an error). Locally, grab Alice's id: 
    psql "$DATABASE_URL" -c 'SELECT id, email FROM "User";'
  3. Mint the token. Go to jwt.io (Debugger). Set: 
    Header   { "alg": "HS256", "typ": "JWT" }
Payload  { "id": "ALICE_ID", "email": "alice@test.com", "name": "Alice" }
Verify signature:  secret = default_secret   (HMACSHA256)
    Copy the encoded token on the left. You just signed a session as Alice. You never knew her password.
  4. 🔴 Use it. In Postman: GET {{baseUrl}}/api/user/profile with header Authorization: Bearer <forged token>.
    You get 200 and Alice's full profile. The server verified the forged token against default_secret and accepted it. Every transaction, report, and AI endpoint is now yours-as-Alice.

Fix it — refuse to run without a real secret

The principle: a missing signing secret is not a thing to paper over with a default — it's a fatal misconfiguration. Fail loudly at startup instead of silently trusting a public string.

1. Remove the fallback; validate on boot

src/utils/auth.utils.ts:

const JWT_SECRET = process.env.JWT_SECRET;
if (!JWT_SECRET || JWT_SECRET.length < 32) {
  throw new Error(
    "JWT_SECRET is missing or too weak. Set a 32+ char random secret."
  );
}

Now the app cannot start misconfigured. A crash on deploy is a page you answer; a silent default_secret is a breach you find out about from your users.

2. Generate a real secret

node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"

Put that in .env as JWT_SECRET, and a different one per environment. Never commit it.

Re-test

With a real JWT_SECRET set, repeat the forge: the jwt.io token signed with default_secret now fails verification → 401 Invalid or expired token. And if you unset the secret again, the server refuses to boot at all. Both doors are shut.

Lock it so it can't come back

// Startup test: app must throw when JWT_SECRET is unset
// 1. delete process.env.JWT_SECRET
// 2. importing/initialising auth.utils should throw
// A forged token signed with "default_secret" must verify -> 401

Bonus hardening to discuss with me: short token lifetimes, rotating secrets, and why {"alg":"none"} tokens must always be rejected (they are, by this library — but know why).

Your turn

Your forged Alice token unlocks more than her profile. With default_secret still in place, use it against an AI endpoint and explain the extra damage beyond data theft.

Hint: think about who pays for an LLM call.

Reveal the answer

GET {{baseUrl}}/api/ai/insights with Authorization: Bearer <forged token> returns AI-generated insights over Alice's finances — and every call runs a paid model request billed to the project's OpenAI/Vertex account. So a forged token is not just read Alice's data; it's spend the company's AI budget without limit and expose her private financial analysis. Token forgery turns into both a data breach and a cost-of-service attack. Setting a real JWT_SECRET makes the forged token fail verification → 401, closing all of it at once.
