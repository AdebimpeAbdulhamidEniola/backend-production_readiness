Deleting a stranger's transactions

Log in as Bob and destroy Alice's financial records — using nothing but a valid Bob token. Then make that attack impossible.

Severity: High OWASP API1:2023 — BOLA

In Part 1 you proved the server can be tricked about who you are. Now we attack the next layer: even as your honest self, the API lets you touch objects that aren't yours. Every endpoint that takes an ID from the client must check the logged-in user is allowed to touch that object. Your transaction endpoints don't — the #1 risk on the OWASP API Top 10.

The claim we're about to prove

Any authenticated user can read the ID of another user's transaction and then update or delete it, because the code looks the row up by id alone and never compares it to req.userId.

Where the hole is

src/models/transaction.model.ts:

export const deleteTransaction = async (id: string) => {
    return await prisma.transaction.delete({
        where: { id }            // ← only the id. whose transaction? nobody asks.
    })
}

And src/controllers/transaction.controller.ts checks you're logged in, then throws the user id away:

const userId = req.userId;
if (!userId) throw new AppError("User not authenticated", 401);
const transaction = await deleteTransaction(req.params.id); // userId never used

Being logged in is authentication. Being allowed to touch this row is authorization. The code does the first and skips the second (Backend-Engineers-Guide/notes/08_security/01_auth.md).

Break it — in Postman

Uses the Alice/Bob setup and TOKEN_A/TOKEN_B from Part 0.

  1. Alice records a transaction. POST {{baseUrl}}/api/transactions, Authorization: Bearer {{TOKEN_A}}, body { "amount": 5000, "category": "Salary", "type": "INCOME" }. Copy data.id → TX_ID. This row is Alice's.
  2. 🔴 The attack. Become Bob: DELETE {{baseUrl}}/api/transactions/{{TX_ID}}, Authorization: Bearer {{TOKEN_B}}.
    You get 200 "Transaction deleted successfully". Bob deleted Alice's data with his own token. Try PUT {{baseUrl}}/api/transactions/{{TX_ID}} with { "amount": 1 } and Bob's token — Bob can rewrite Alice's money too.
  3. Confirm the damage. As Alice, GET {{baseUrl}}/api/transactions — her transaction is gone. She never consented.

No special tools — just an ID Bob wasn't supposed to use. This is how real breaches pull thousands of other users' records.

Fix it — scope every object to its owner

In every function that uses a client-supplied input to reach a record, check the logged-in user owns it. We push the user's id into the query so the database can only ever touch their rows.

1. Make the model owner-aware

export const updateTransaction = async (
  id: string, userId: string, data: Partial<TransactionInput>
) => {
  const result = await prisma.transaction.updateMany({
    where: { id, userId },   // ← must match the owner too
    data,
  });
  return result.count;       // 0 = not yours (or not found)
};

export const deleteTransaction = async (id: string, userId: string) => {
  const result = await prisma.transaction.deleteMany({ where: { id, userId } });
  return result.count;
};

2. Make the controller enforce it

const count = await deleteTransaction(req.params.id, userId);
if (count === 0) throw new AppError("Transaction not found", 404);
handleResponse(res, 200, "Transaction deleted successfully");

Do the same in updateTransacctionController. Return 404, not 403: a 403 would confirm the row exists and leak that another user has it. 404 reveals nothing.

Re-test — same requests, new outcome

Bob's DELETE on Alice's {{TX_ID}} → 404 "Transaction not found". Then delete it as Alice → 200. Owners can act; strangers can't.

Lock it so it can't come back

// Bob must NOT delete Alice's transaction
// DELETE /api/transactions/:aliceTxId  with Bob's token -> 404
// and Alice's transaction still exists

We turn this into a runnable test in Lesson 4, and CI runs it on every push.
