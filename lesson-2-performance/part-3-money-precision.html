When ₦0.10 + ₦0.20 isn't ₦0.30

Your amounts are stored as floating-point numbers. For a finance app, that's a correctness bug waiting to happen. You'll make the computer get money wrong, then fix how it's stored.

Study & Check — do this before the practical

Read: this is a correctness topic the guide doesn't cover directly, so the source is the language itself — run the "break it" step below first, then read MDN on Number (floating point). Core idea: computers store decimals in binary, and most decimal fractions (like 0.1) can't be represented exactly — so arithmetic drifts by tiny amounts.

Impact: Correctness (money!)

Where the issue is

prisma/schema.prisma stores amounts as Float:

model Transaction { amount Float }         // ← floating point
model User { monthlyIncome Float?  savingsGoal Float? }

And the report sums them in JavaScript: reduce((total, t) => total + t.amount, 0). Floats + many additions = drifting totals.

The claim we're about to prove

Adding many float amounts produces a total that is slightly wrong — off by fractions of a unit. In money, "slightly wrong, repeatedly" is a serious bug.

Break it — watch the math drift

  1. The one-liner everyone should see. In a Node REPL (node) or your browser console: 
    0.1 + 0.2            // → 0.30000000000000004
0.1 + 0.2 === 0.3    // → false
  2. Make your API do it. As Alice, create three transactions: 0.1, 0.2, 0.1 (all INCOME). Then call GET {{baseUrl}}/api/reports/monthly.
    The totalIncome can come back as 0.4000000000000001 instead of 0.4. Scale that across thousands of transactions and real balances stop matching. A finance API that can't add money correctly is broken, no matter how fast it is.

Fix it — store money as whole numbers

The professional default: store money as integer minor units — kobo (₦) or cents ($). ₦1.00 becomes 100. Integers add exactly; no drift ever.

1. Change the schema

model Transaction {
  amountMinor Int      // e.g. 100 = ₦1.00 ; always exact
}
model User {
  monthlyIncomeMinor Int?
  savingsGoalMinor   Int?
}

2. Convert at the edges only

// incoming: ₦ from client → minor units for storage
const amountMinor = Math.round(amountNaira * 100);
// outgoing: minor units → ₦ for display
const naira = amountMinor / 100;

All math (sums, reports) happens on the integers; you only divide by 100 at the very end for display. The database never holds a fraction.

Alternative

If you'd rather keep decimals, use Prisma's Decimal type (fixed precision) instead of Float, and do arithmetic with a decimal library. Integer minor units is simpler and the more common choice for transactional money.

Re-test

Store 0.1, 0.2, 0.1 as 10, 20, 10 (minor units). The report sums them to 40 exactly, and you display ₦0.40. No drift, ever — because you never added floats.

Your turn

Changing Float to Int is a breaking schema change — existing rows hold values like 5000.0. What has to happen to that old data, and why can't you just change the column type?

Reveal the answer

You need a data migration: a script/SQL step that multiplies every existing amount by 100 and writes it into the new integer column, before (or as part of) dropping the old one. Just switching the type would misread 5000.0 as 5000 minor units (= ₦50.00) instead of ₦5000.00 — off by 100×. Real production changes like this ship as: add new column → backfill (multiply) → switch reads/writes → remove old column. This is exactly the kind of careful, reversible migration Lesson 3 (Reliability) and Lesson 4 (CI/CD) make safe.
