The query that reads every row

Every "get my transactions" makes the database look at every transaction in the whole table — because there's no index on userId. You'll see the full scan, then kill it.

Impact: Slows with scale

Where the issue is

Your Prisma schema (prisma/schema.prisma) defines Transaction.userId but puts no index on it. Yet every transaction read filters by it:

prisma.transaction.findMany({ where: { userId } })   // filters on an unindexed column

So Postgres scans the entire Transaction table every time. Same for the report query that filters by userId + createdAt.

The claim we're about to prove

Filtering by userId triggers a sequential (full-table) scan. You'll see Postgres say so, and watch it get slower as the table grows.

Break it — ask Postgres what it's doing

With the ~5,000 rows you seeded in Part 1, run EXPLAIN ANALYZE (via Prisma Studio's query console, psql, or any DB client):

EXPLAIN ANALYZE SELECT * FROM "Transaction" WHERE "userId" = 'ALICE_ID';
You'll see Seq Scan on "Transaction" — Postgres is reading every row and checking each one. The bigger the table, the worse the time. That phrase, Seq Scan, is the smoking gun.

Fix it — add the index

1. Declare it in the schema

model Transaction {
  // ...existing fields...
  userId    String
  createdAt DateTime @default(now())

  @@index([userId])                 // speeds "my transactions"
  @@index([userId, createdAt])      // speeds the monthly report (userId + date range)
}

The composite [userId, createdAt] helps the report because its query filters by userId first (the leading column) and then a date range — exactly the order the guide says a composite index needs.

2. Create and apply a migration

npx prisma migrate dev --name add_transaction_indexes

Re-test

Run the same EXPLAIN ANALYZE: the plan now shows an Index Scan (or Bitmap Index Scan) instead of Seq Scan, and the execution time drops sharply. Postgres jumps to Alice's rows instead of reading the whole table.

Your turn

You added @@index([userId, createdAt]). Would a query that filters only by createdAt (no userId) use that index? Say yes/no and why.

Reveal the answer

No. A composite index only helps queries that use its leading column(s). [userId, createdAt] is ordered by userId first, so a query filtering only on createdAt can't jump in — it would fall back to a scan. If you frequently query by date alone, you'd need a separate @@index([createdAt]). This is the guide's "leading column" rule, and a classic interview question.
