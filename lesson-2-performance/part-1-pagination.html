The list that returns everything

Your transactions endpoint hands back every row a user has ever created — in one response. Fine with 3 rows; a problem with 50,000. You'll prove it, then page it.

Impact: Scales badly

Where the issue is

src/models/transaction.model.ts — the list has no limit:

export const getTransactionsByUser = async (userId: string) => {
  return await prisma.transaction.findMany({ where: { userId } });  // ← every row, always
};

The controller even admits it: // I would still implement Pagination in this controller. Let's do that.

The claim we're about to prove

As a user accumulates transactions, GET /api/transactions returns all of them in one response, and the response gets steadily slower and larger — unbounded.

Break it — feel the growth

  1. Seed a lot of rows for Alice. In a terminal (adjust the connection as needed), or add a quick loop to prisma/seed.ts: 
    // seed 5,000 transactions for one user, then run: npx tsx prisma/seed.ts
for (let i = 0; i < 5000; i++) {
  await prisma.transaction.create({ data: {
    amount: Math.random()*100, category: "Test", type: "EXPENSE", userId: ALICE_ID,
  }});
}
  2. Call the endpoint as Alice: GET {{baseUrl}}/api/transactions. Watch two numbers in your server log:
    The response time climbs (tens → hundreds of ms) and the payload size balloons to megabytes. Now imagine 500,000 rows, or every user hitting it at once. The endpoint has no ceiling — that's the bug.

Fix it — paginate

Return a bounded page, and let the client ask for the next one.

1. Accept page params and cap them

Controller (getTransactionController): read page and limit from the query, with safe defaults and a hard maximum:

const page  = Math.max(1, Number(req.query.page) || 1);
const limit = Math.min(100, Math.max(1, Number(req.query.limit) || 20)); // cap at 100
const skip  = (page - 1) * limit;
const result = await getTransactionsByUser(userId, skip, limit);

2. Bound the query

export const getTransactionsByUser = async (userId: string, skip: number, take: number) => {
  const [items, total] = await Promise.all([
    prisma.transaction.findMany({ where: { userId }, skip, take, orderBy: { createdAt: "desc" } }),
    prisma.transaction.count({ where: { userId } }),
  ]);
  return { items, total };
};

Return { items, total, page, limit } so the client knows how to ask for the next page.

Re-test

GET {{baseUrl}}/api/transactions?page=1&limit=20 → fast, small, 20 rows no matter how many exist. ?page=2 → the next 20. The endpoint now has a ceiling: response size and time stay flat as data grows.

Your turn

A client sends ?limit=100000 to pull everything in one shot. Does your fix stop them? Prove it, and explain why the cap matters.

Reveal the answer

Call GET {{baseUrl}}/api/transactions?limit=100000. Because of Math.min(100, ...), the server clamps it to 100 — you still get at most 100 rows. Without that cap, a client (or attacker) could set a huge limit and reintroduce the exact unbounded-response problem on demand — turning a performance control into a denial-of-service lever (ties back to Lesson 1 Part 4). Always cap limit server-side; never trust the client's number.
