Doing in Node what the database does better

Your monthly report downloads every transaction into your server's memory and adds them up in JavaScript. The database can do that sum far faster, before the data ever leaves it. You'll prove the waste, then push the work down.

Impact: Wasteful at scale

Where the issue is

src/controllers/report.controller.ts — it pulls every transaction into Node, then filters and sums in JavaScript:

const transactions = await getTransactionsByUser(userId);   // ALL rows into memory
const monthly = transactions.filter(/* this month */);
const totalIncome   = monthly.filter(t => t.type==="INCOME").reduce((s,t)=>s+t.amount,0);
const totalExpenses = monthly.filter(t => t.type==="EXPENSE").reduce((s,t)=>s+t.amount,0);

To produce two numbers, it downloads every row. (The category report in report.model.ts already does it the right way with groupBy — compare them.)

The claim we're about to prove

The monthly report's cost grows with the user's total number of transactions, even though the answer is just a few totals — because it moves all rows into Node to add them up.

Break it — see the waste

  1. With Alice's ~5,000 seeded rows, call GET {{baseUrl}}/api/reports/monthly and note the time in your server log.
  2. Seed 20,000 more and call it again.
    The time climbs with the row count — because every call drags all those rows across the connection into Node just to compute 3 numbers. The work scales with data it shouldn't need to.

Fix it — aggregate in the database

Ask Postgres (via Prisma) to compute the sums and return only the totals.

// report.model.ts
export const getMonthlySummary = async (userId: string, start: Date, end: Date) => {
  const grouped = await prisma.transaction.groupBy({
    by: ["type"],
    where: { userId, createdAt: { gte: start, lt: end } },
    _sum: { amountMinor: true },          // DB does the sum
  });
  // grouped → [{ type: "INCOME", _sum: { amountMinor: 40000 } }, ...]
  return grouped;
};

The controller then just reads the two numbers out of grouped and computes savings. Only a handful of rows ever cross the wire, and the [userId, createdAt] index from Part 2 makes the filter fast.

Re-test

GET {{baseUrl}}/api/reports/monthly stays fast whether the user has 50 or 50,000 transactions — because the database returns only the totals, not the rows. Cost now scales with the answer, not the data.

Your turn

The category report (getCategoryWiseSpending) already uses groupBy. Open it and explain, in one line, why it was already "correct" by this lesson's standard — and what it returns instead of raw rows.

Reveal the answer

It uses prisma.transaction.groupBy({ by: ['category'], _sum: { amount: true }, where: {...} }) — so the database groups by category and sums each group, returning just one row per category (category + total), not the raw transactions. That's the same "push the work down, return small results" principle this part applies to the monthly report. Your previous self got the category report right and the monthly report wrong — fixing the monthly one makes them consistent.
